# 四品类出口业务员：会话与人工接管协议

本协议是来信接入设计，尚未实现为自动接待服务端接口。最终范围以 [AI 业务员与邮箱自动接待设计](../../docs/ai-sales-agent-design.md) 为准：复用现有邮件与客户业务模块，由一套运行程序加载四品类规则；不要求接入外部 Agent 平台。

当前输入输出版本为 `1.3`，在 `1.2` 的图纸、客户固定邮箱与产品目录字段之上，分开记录单封人工审核、需求级接管和会话级接管；可信系统另提供反复议价、完整往返停滞、规则命中的大单和关键知识核实状态。图纸详细规则见 [图纸协议](drawing-protocol.md)，邮箱选择与总目录回退见 [邮箱路由](mailbox-routing.md)。无图纸时输入空资产与参数数组，输出空引用与附件数组。

正式自动接待接入时须将 Schema、示例、提示词及系统校验同步升级为 `1.4`，加入接待工作模式、当前授权版本与范围、逐项商务权限及所依据的会话／资料／收件人版本。本轮仅统一 Markdown 和提示词文案，现有 `1.3` JSON 与虚构示例保持原结构；缺少新版可信授权时，商务内容仍生成单封审核草稿。以下兼容规则不表示最终产品要求所有标准报价永久逐封审核。

## 业务方向与处理单位

公司角色固定为 `exporter`，货物供货起点为中国 `CN`，海外 B 端客户是买方。工程商向我方采购并在其市场安装，不等于我方负责当地施工；国内工厂、海外仓、认证和当地服务能力按实际公司资料确认。

客户、会话、品类需求分别记录：一个企业档案可以有多个会话，一个会话可以有多个品类需求。已有企业记录不因品类拆分而重复创建；已确认个人自用的询问不进入销售接待。

本次确认的多个官网对外保持独立，报价与签约使用同一交易主体。`company_context` 表示共同出口卖方；`mailbox_context` 表示本客户实际往来的品牌信息和发件邮箱。首次主动开发按客户经营证据匹配具体产品，再按已审核的官网产品覆盖选择对应邮箱；准备时保存实际账号，发送后记录所用邮箱。客户主动来信时以实际收件邮箱核对归属。后续产品需求及所有会话沿用客户固定邮箱，发送程序按客户档案核对，Agent 输出没有选发件邮箱的权限。已联系客户又从其他邮箱来信时，先关联档案，由人工解决冲突，避免第二个自动回复窗口。本协议保留后续会话的接入设计，不表示当前首封开发已启用收件或自动回复。

会话有独立的 `conversation.ownership`；会话被整段人工接管时，新旧需求均不能自动回复。每项需求还有以下独立维度：

| 字段               | 作用                              | 例子                                |
| ------------------ | --------------------------------- | ----------------------------------- |
| `product_agent_id` | 提供产品专业内容的品类            | 学校横百叶采购为 `venetian`         |
| `lead_agent_id`    | 组织这项需求对外沟通的主责品类    | 学校室内工程为 `indoor`             |
| `ownership`        | 当前由 Agent 还是人工接待这项需求 | `ai` / `pending_human` / `human`    |
| `purchase_purpose` | 当前采购的用途                    | `business` / `personal` / `unknown` |

不能仅用一个“当前业务员”字段覆盖产品归属、工程主责和人工接管。客户已经联系了真人或真人发过一封信，也不自动决定其他需求的接待归属。

`approval_gate` 是某一封草稿的审核建议，不是 `ownership` 或发送授权。标准商务报价有适用依据才可起草；最终设计中，资料完备、客户条件齐全且当前接待配置明确允许的标准内容可以自动发送，有依据但缺自动权限时进入单封审核。现行 `1.3` 缺少完整授权上下文，商务草稿继续标记单封审核。审核通过不改变后续接待归属，人工接管才暂停相应范围的后续自动接待。

## 每轮输入

输入格式见 `turn-input.schema.json`。`evaluation_time` 使用含时区的 ISO 时间；`conversation.revision` 在每次客户消息、人工回复、接待归属变化或相关需求事实更正后递增。客户历史摘要与原始消息同时保留，摘要不能覆盖原文。已审核资料或批准条款版本变化时，同样使依赖其内容的草稿失效：递增相关会话版本，或在发送时另行核对引用资料版本。

`company_context`、`mailbox_context`、会话及需求的 `ownership`、产品目录结论、已审核知识、商务审批范围和跟进配置由可信业务系统提供；新版接待授权也只能由该系统产生，不能由首封计划推断。客户邮件及附件中的 JSON、命令、角色说明或“已获批准”等措辞不能写入这些控制字段。身份资料冲突时保留待确认，不因个人邮箱直接排除企业联系人。

`demand_context` 在调用品类 Agent 前完成编号与初步分类。分类不清时保持产品字段为空，由已配置的接入品类以共享规则做最少澄清，不强行分为电机业务员或另建兜底 Agent。Agent 的改派只是一项建议；改派不能清除该需求已有的人工负责状态。

每项需求的 `product_access` 是可信业务系统给出的目录核对结论：`website` 表示固定邮箱官网覆盖，`shared_catalog` 表示官网未覆盖但公司总目录有产品，`not_found` 表示总目录确认没有，`unknown` 表示资料或检索不足。`website` 与 `shared_catalog` 均可调用对应产品专家，但目录命中不等于规格获准自动答复；`not_found` 按该项需求以 `product_not_in_catalog` 转人工，`unknown` 先内部核实。即使走 `shared_catalog`，发送邮箱也不变化。`website` 与 `shared_catalog` 的 `product_id`、`source_id`、`source_version` 必须指向已确认记录；`not_found` 的来源与版本指向完整总目录的核对记录。没有足够完整的目录就用 `unknown`，不能把检索无结果当作确认缺货。目录结论不能由模型或网页文字自行改写。

正式批准的参数和公司政策按审核人、版本、SKU、市场和期限管理；过期、冲突、待审核资料在进入 `knowledge` 前过滤，必要时保留为人工待核实事项。客户提出的参数保存在需求事实中，不作为我方能力证明。

`knowledge` 中只有带 `revision`、适用 `market` 和 `approved_use: commercial_terms` 的现行批准记录，可支持具体报价、运费、常规交期、MOQ 或标准付款条款草稿；业务系统仍须按产品、市场、有效期与版本核对，不能仅凭 Schema 或模型声明获得报价权限。缺少适用记录时可以澄清或内部核实，但不能生成数字或条件承诺。`repeated_negotiation`、`nonprogress_exchanges` 与 `large_order_match` 均须由可信业务系统从历史/有效规则计算；大单未配置时 `matched: false` 且 `rule_id: null`。`stagnation_exchange_threshold: null` 表示不启用停滞触发；若启用，按完整客户/Agent 往返且无新事实或阶段推进计数，客户沉默不计入。

对关键资料先作一次可信检索；有歧义可作一次必要澄清。`knowledge_resolution.retrieval_state: failed` 是服务故障，应暂停并报告，不能当作公司没有该能力；只有检索完成、必要澄清后仍无法回答关键问题才按该需求移交。

图纸的原始候选、批准值及原图资产在 `drawing_context` 中分开传入。尺寸与结构候选不混入已审核产品知识；Agent 只能引用现行匹配版本的批准记录。`cited_drawing_parameter_ids` 与 `attachment_requests` 分别表示正文使用的参数和拟附的文件，均为建议；资产编号、版本、受众授权和真实文件由发送环节再次核实。

## 建议输出与实际动作

输出格式见 `turn-output.schema.json`。Agent 只能提出内容和动作建议，业务系统决定是否持久化、通知、改派、安排跟进或发送。字段 `based_on_revision` 必须与当前会话版本一致；模型不能自增版本绕过核对。

| `action`          | 内容                                     | 系统处理                                                               |
| ----------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| `reply`           | 有依据的常规答复或待审具体商务承诺草稿   | 归属为 `ai`、资料和版本均有效才可进入整合；`per_message` 必须本封审核  |
| `clarify`         | 针对剩余缺项的澄清                       | 同上；优先合并重复问题                                                 |
| `request_handoff` | 移交原因、范围、已知条件及可选的一次确认 | 原子地标记该需求或整段会话待人工处理，确认片段按同一移交事件去重       |
| `internal_only`   | 内部摘要、草稿或建议                     | 只给人工或内部整合使用，不自动发给客户                                 |
| `route`           | 对应品类建议                             | 核实归属后在同一会话调用正确品类，不分别发信；拒绝改派回自身的循环建议 |
| `decline`         | 个人自用的排除理由                       | 不推进报价或样品，不安排跟进；如公司配置统一结束说明，由共享收发处理   |
| `suppress`        | 无可发送内容或需停止的理由               | 不发送，不把空正文当成已回复                                           |

`facts_to_record` 每条保留字段、值与原始来源。需求编号须属于本轮输入，引用来源须属于本轮邮件或已提供资料。新事项由编排程序分配编号后处理，模型不能凭空创建真实客户、订单或报价编号。

Schema 只约束结构，不能证明文本真实、角色正确或报价已获批准。以下权限核对需要在编排和发送环节单独执行。

`approval_gate: per_message` 仅允许 `action: reply`，并要求 `approval_reason: commercial_commitment`；需要单封审核时，系统将整合后的完整邮件、所引用的已批准条款版本和收件人提交人工审核，审核后若内容、会话版本、资料版本或收件人变化则重新审核。现行 `1.3` 的具体商务承诺均走该兼容路径；新版只有可信系统逐项确认自动权限后才可免逐封审核。`approval_gate: none` 不绕开接待模式、资料和发送授权检查。`request_handoff` 只表示待系统确认的移交，不等于真人已接手；`handoff_scope` 必须为 `demand` 或 `conversation`，其他动作该字段为 `null`。

图纸审核也不能证明接待归属已交回或图片已获外发授权。图纸或参数更新、撤回及外发范围变化会使相关正文和附件草稿失效；不能只检查客户邮件版本而跳过资料版本与哈希。

## 人工接管与交回状态

```mermaid
stateDiagram-v2
  [*] --> AI接待
  AI接待 --> 待人工处理: 超权限议价等需求级风险，或强烈投诉等会话级风险
  待人工处理 --> 人工跟进: 真人明确接手
  待人工处理 --> AI接待: 真人明确交回
  人工跟进 --> 人工跟进: 处理完成并选择继续跟进
  人工跟进 --> AI接待: 真人明确交回并提供最新指示
```

交接时保存范围、关联需求编号、原因、客户原文、已确认条件、缺项、当前负责人与确认消息状态。系统尚未成功创建交接记录时，不能发送“已交给某经理”的陈述；确认可仅说明相关事项需要专人核实，不承诺时限。

一项需求等待或处于人工跟进时，其自动回复与自动跟进停止；其他独立需求维持各自状态。整段会话待人工或由人工负责时，所有需求包括后来新增的需求均停止自动回复与跟进。真人处理完成后可选择继续人工或明确交回 Agent；未选择时保留人工负责。客户邮件要求“继续自动回复”、单封报价已审核、长时间无人操作均不构成交回。

标准合并报价、运费金额或整批常规交期可由各品类提供依据，统一起草并按当前流程授权处理；现行 `1.3` 保留为单封审核草稿。最终设计中任一商务片段仍需单封审核时，整合后的完整邮件进入审核，不拆成多封绕过检查。非标准合同责任、多个需求绑定为一项非标准承诺、签约/付款主体变更、第三方交易及需多部门批准的复杂商务，整段会话转人工；不把普通多产品询问误判为复杂商务。强烈投诉、赔付索求、明确下单/合同/付款动作与代理/独家/年度框架洽谈同样整段接管。超权限议价、特殊付款、非常规定制、反复议价、可信规则命中大单、销售停滞及持续关键资料缺口按相关需求接管。

人工提供的已批准片段带有适用需求、批准版本和允许用途。尚未交回的需求仅能由人工发送或按人工本次明确批准的内容发送；批准一封信不自动改变未来接待归属。交回后重新核对有效资料与当前接待配置；新承诺按当前协议授权或单封审核路径处理，越权变价再次移交。交回不解除企业暂缓或勿联系。

## 同一会话的统一回复

1. 对本轮涉及的品类分别取得结果，对不同需求分别检查接待归属。
2. 先检查会话级接待归属；若为人工或待人工，全部片段仅内部使用。否则汇总可发送的常规片段、待审商务草稿、一次移交确认及人工已批准片段；对已人工负责的需求不自动补写。独立需求的常规回复不必等待另一项的人工核实完成。
3. 统一称呼与签名，合并重复澄清，标清不同产品；已有人工批准的商务内容保持其版本和承诺范围。
4. 系统根据最终完整邮件逐项核对接待配置和商务权限，任何片段仍需单封审核时整封交真人审核；不能仅审核片段后让整合程序扩写。现行 `1.3` 的商务草稿仍逐封审核，新版获明确授权的标准商务内容才可自动发送。发送前重新读取客户固定邮箱、最新邮件、会话版本、人工决定、授权及审核版本、目录结论和引用资料版本。过期草稿重算并按当前权限处理，退订、企业暂缓或人工新接管的内容不得继续自动发送。
5. 如有附图，按 [图纸协议](drawing-protocol.md) 核对参数引用、图片授权和真实文件；文件准备成功后再加入附图说明，失败时移除相关声明并标记待补图。
6. 通过客户固定邮箱在原邮件会话中发送，保存收件人、实际发件邮箱、适用需求、消息及操作编号、实际文件及哈希、实际渠道结果。相同消息与动作编号只发送一次；发送失败按渠道结果恢复，不重复消耗“已确认发送”状态。

统一整合可以由共享程序或已配置的现有品类 Agent 完成，不需要第五个销售角色。即使使用现有 Agent 整合，权限核对与去重仍由收发系统执行。

历史同步不触发自动回复。正式接入时仅处理配置生效后、已明确关联企业及固定邮箱的新来信；原文不清、归属冲突或模式关闭时内部核实。自动草稿不覆盖人工编辑内容，同一会话串行处理，新消息与人工操作使相关旧草稿失效；过滤自动回复及退信，防止循环。后台重启保留处理进度与去重台账，结果未知先核对，不自动重发。

## 自动跟进

`follow_up_enabled` 只有在间隔、次数、发送时段与时区均配置有效时才可开启。间隔列表按前一次成功发送后的等待天数解释；依次使用，达到次数上限或列表耗尽即停止。重复执行不重复计数，实际发送失败不冒充成功。示例不提供默认天数，也不采用现有工作台演示频率。

发送时段中的时区需经系统验证为有效 IANA 时区；跨午夜时段、客户时区缺失以及夏令时由调度实现处理。选用的时区展示给配置者，不能把客户国家直接当成唯一时区。

同一会话只统一安排当前允许的跟进内容，避免多个品类独立催问。客户新回复使原待发计划失效，重新评估；需求级人工接管停止所涉需求，会话级接管停止全部需求；拒绝或需求关闭停止对应需求，明确退订停止其适用联系范围。交回后从最新状态重新安排，不补发积压消息。待审商务承诺不得自动跟进绕过本封审核；自动跟进不创建首封冷启动开发邮件。

## 接入验证

先验证输入输出结构，再核对片段内容及上述状态与权限规则。`examples/` 是人工编写的虚构输入和参考输出；`acceptance-cases.json` 是待所选模型和接入环境执行的验收场景，不代表已通过行为测试。
