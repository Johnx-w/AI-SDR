# GitHub 方案复用评估：ShadeFlow 外贸窗饰获客

核查日：2026-10-24。来源为官方仓库、许可证、发布记录和部署文档；版本通过 GitHub API 只读核对。本文未安装或压测候选软件，近期提交、正式发布和功能文档只说明可继续评估，不代表已经验证本项目的生产可靠性。工时和运维投入是规划估算，不能视为供应商报价。

评估口径更新：用户确认海关 API 和大模型费用由公司报销，无需优先压低这两项单价。选型以公司总投入为准，优先比较开发时间、持续维护、可靠性和合格客户的稳定产出。下文费用统计和回本公式保留为可核查的成本工具，不据此牺牲研究质量或增加不必要的自托管工作。

## 对当前项目的结论

**保留现有 Node.js 直连主流程；直接复用成熟基础库，业务判断继续放在 ShadeFlow。按开发、维护和稳定产出的总投入选择组件，不把降低 API 单价放在首位。** n8n、Dify、Firecrawl、Twenty 和 Chatwoot 分别解决编排、模型应用、网页抓取、CRM 和客服收件箱，叠加后仍要编写本项目的产品准入、证据核验、评分和邮件授权代码，还会增加数据库、队列、账号和升级工作。对于直接读取失败的网页，托管抓取服务若能减少维护并提高成功率，可以比自托管更合算；Crawlee 等自建兜底仅在有实际质量、稳定性或总投入收益证据后接入。

现有代码已经有如下资产，评估迁移成本时应计入：

- [native-acquisition.mjs](../../server/native-acquisition.mjs) 先直接读取官网和发现的站内页面，最多五页；失败页面才调用 Tavily `basic extract`。所以“所有网页都要付费抓取”不是当前成本基线，开源爬虫能替代的主要是失败兜底部分。
- [research-input.mjs](../../server/research-input.mjs) 已限制研究输入为最多五页、每页 16,000、合计 80,000 个 UTF-16 代码单元；这不是 token 总预算。[research-reuse.mjs](../../server/research-reuse.mjs) 为精确研究请求生成缓存键，调用与缓存命中已有统计。
- [自动评分说明](../automatic-assessment.md) 明确模型提取事实及原文，程序按 P40/R30/D20/V10 评分；海关采购表现独立分析。通用 CRM 的 lead score 不能直接替代。
- [四品类 Agent 说明](../../agents/export-sales/README.md) 当前交付主要是提示词、协议和规则资产，模型、客户库、人工通知与定时跟进尚未接通；不能把“有四份提示词”算成已上线四名业务员。
- [ADR-0002](../adr/0002-web-primary-operational-interface.md) 选择网页作为主要操作入口、飞书作为协作资料同步；[ADR-0007](../adr/0007-isolate-mailbox-pilot-from-real-outreach.md) 仅允许固定双公司地址技术试点。更换收件箱或连接 SMTP 不会自动完成真实触达授权。

## 哪些可以直接复用，哪些仍要自研

| 层次               | 建议                                                                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通用网页抓取       | 继续复用已有 Node HTTP；需要 JS 渲染时在 Crawlee/Playwright 与按量托管兜底中择一，不同时上多个抓取平台。限制到已选企业官网，保留来源和原文。                          |
| 调度、持久化与重试 | 继续现有 SQLite 队列和调度；不因开源平台免费再维护一套任务状态。任务扩大到单机资源上限后才讨论 worker/队列迁移。                                                      |
| 模型协议与正文     | 继续现有服务商适配、Schema、精确缓存、正文上限及调用统计；模型产生事实，规则程序评分。                                                                                |
| 邮箱底层           | 项目已依赖 `imapflow`、`mailparser`、`nodemailer`（见 [package.json](../../package.json)），继续直接复用协议库；它们不提供投递信誉、不代替商务授权。                  |
| 业务核心           | 自研并复用现有实现：企业身份和来源合并、供货方向、必需/优先条件、事实与引文核验、P/R/D/V 初评、评估版本/历史、海关独立关联、客户固定邮箱、需求/会话接管和发送前校验。 |
| 团队基础功能       | 登录、角色、备份和操作审计可采用成熟组件；不要因为当前尚未实现就立即整体迁入另一套 CRM。                                                                              |

## 部署维护与回本判据

以下只是用于决策的增量规划，不是已完成评测：

| 路径                              | 增量工程估算                                                                  | 维护代价及选择条件                                                                 |
| --------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 保持原生，按量兜底                | 最小；先补失败率、兜底页数、合格新增成本看板                                  | 当前进程和数据库备份、密钥与依赖更新；只维护一条主链。小批量通常最容易控制总投入。 |
| 加 Crawlee 浏览器兜底             | 约 2–5 个开发日，含适配、限流、URL 安全、原文一致性与异常样本验证             | 增加 Chromium 版本、内存/超时和网页变化维护；不能只比较每页 API 单价。             |
| 独立 Crawl4AI 服务                | 约 3–7 个开发日，含部署与 Node 适配、同样的边界验证                           | 额外 Python/Docker/浏览器运行时；只有成功率或正文质量收益显著时值得。              |
| 自托管完整 Firecrawl / Dify / CRM | 不能按“Docker 一键启动”当成项目交付；需另算认证、备份恢复、版本升级和业务迁移 | 业务字段、同步及权限映射决定主要工时；当前没有充足样本支持给可靠天数或低月费承诺。 |

自建兜底的月回本条件应使用：

`每月实际节省的付费兜底支出 > 新增服务器/浏览器/代理支出 + 运维小时 × 内部工时单价 + 一次性开发费 ÷ 预计摊销月数`。

分母必须是**去重后、达到销售交接条件的新增企业数**，同时看待核实率和人工纠错时间。抓取到更多网页、邮箱或企业名称，不等于得到同样多合格客户。若当前免费额度尚未用完，或者付费兜底本来很少，立即自建浏览器服务甚至可能增加总成本。

## 实施顺序

1. 在现有链路采样至少一组稳定市场与产品任务，统计直接读取成功率、付费搜索/提取信用点、模型 token、合格新增数与重复率；复用已有计数，避免重复发起付费研究。
2. 用历史失败页、JS 页和正文不足页离线对比 Node 直读、Crawlee 和一种托管兜底。保持同样页数和事实核验规则，不能用“HTTP 200”判定研究成功。
3. 只有回本公式为正且证据质量不下降才接 Crawlee；否则继续直接读取 + 按量兜底。
4. 等确有多人协作痛点再单独决策 CRM/团队收件箱；等知识资料达到规模且非开发人员频繁编辑时再决策 Dify。

本报告只修改研究文档，没有安装服务、修改项目配置、创建 GitHub Issue、触发业务 API、发送邮件或提交代码。
