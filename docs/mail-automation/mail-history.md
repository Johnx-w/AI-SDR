# 历史来信与只读同步

在跟进任务中选择「邮箱来信跟进」，或打开 `/business?view=replies`。列表从当前服务使用的 SQLite 读取，单页 25 封，点击主题在收件箱打开同一账号的同一线程。原自动追信任务可以按客户查看来信，按发送计划查看执行记录。

## 查看依据

在「客户回信」下可用「处理情况」筛出待跟进或已有回复的邮件。没有明确业务内容、只有通用收件承诺的回执单列在「待核实回执」。客服工单标记、明确的系统回执正文及标准自动回复头用于识别通知。可疑回执留给业务员核对。

「业务分类」在收件箱、来信跟进和沟通台账之间共用。积极回复进一步标记索价、索目录或约见；其余分为明确拒绝、渠道转介、客服通知、退信、待核实和其他真人回复。判断只使用客户本次正文，排除回复头之后或引用块中的我方历史内容。客服工单分隔线上方若有客户新写的请求，以该请求为准；只有工单正文或自动受理证据时归客服通知。筛选上方的计数与当前邮箱、来信类型和处理状态范围一致。

正式 CRM 来信列表同时返回逐封的 `businessKind`、`requestType` 和该范围的 `businessCounts`。原 T3 按轮次保留记录及关联，使用两个多选字段「回信分类」「客户请求」。数字字段「积极回复封数」「明确拒绝封数」「渠道转介封数」「客服通知封数」「退信封数」「待核实封数」「其他真人回复封数」按列合计，可与同一批 CRM 来信逐封核对。

未处理的索价、索目录和约见同时出现在运营总览的「积极回复待办」。等待时间从来信收件时间起算。系统仅以同一邮箱、同一来信编号和同一客户地址的已发邮件作为实际回复证据；草稿不算。若已通过电话、WhatsApp 或线下完成，在收件箱把会话标为「已完成」即可结束；之后同线程有新的积极来信时会重新打开。首次读取旧缓存时同样核对既有已发件和会话状态，不为已处理历史重新催办。

- 「客户回信」要求 IMAP 收到入站邮件、有有效 In-Reply-To 或 References，且排除了已识别的通知、退信、退订、投诉和内部往来。列表显示邮箱实际收到的来信，不验证发件人的法律身份。没有本地原发件时，保留真实回复头并显示“未找到本地原发件”。无回复头的来信可从单独筛选查看。
- 客户名称仅来自已知客户地址的唯一匹配。无匹配或多个同地址客户时显示原发件地址。绑定账号之间的邮件归入内部往来，其中带内部 QA 标记的邮件归入内部测试。
- 查看本邮箱发给该对方的后续邮件时，核对其 In-Reply-To 或最后一个 References 是否指向这封来信的 Message-ID。已有人工/自动提交记录时显示具体处理方式；只有原邮箱发件证据时显示“邮箱已回复”。没有可核对的后续邮件时，客户回信显示“待跟进”。一次新建邮件、改主题另起线程或遗漏已发件历史都可能缺少可核对的关联。
- 分类基于邮件头、发件地址及通知特征。阿里 IMAP 读取完整邮件头来识别 `Auto-Submitted`，超过解析上限的来信保留信封和正文并标记待核实。此列表不会创建 CRM 客户、发送计划或发件任务。历史未回复列表和自动追信任务分别保留自己的业务含义。

## 本机独立同步

使用本机加密邮箱注册文件所在的隔离数据目录。目录需要独立的 `mailboxes.json` 和 `outreach.sqlite`，新建数据库时只初始化会话和来信索引。若使用已有库，先按 SQLite 一致备份方式准备快照，保持邮箱 ID 和注册信息一致。Windows DPAPI 凭据应由可解密它的同一用户在本机运行。显式指定目录后，工具只加载该目录的邮箱注册文件。

```powershell
node scripts/sync-mail-readonly.mjs --data-dir D:\mail-review\outreach
node scripts/sync-mail-readonly.mjs --data-dir D:\mail-review\outreach --mailbox <邮箱ID> --since 2026-01-01 --rescan --max-pages 40
```

每次每个文件夹最多处理 50 封；每邮箱最多读取 `--max-pages` 批。默认尝试完成至多 40 批。首次默认最近 30 天，有游标时从原位置继续。指定更早的起点会扩展范围，`--rescan` 从指定起点重新读取以补存回信头。没有提供新的起点时，回扫使用原起点。达到批次上限仍有更多内容时，不带 `--rescan` 重跑即可继续。输出中的 `imported` 仅统计新增本地消息，已存邮件的头部补录不计为新增。

工具使用阿里企业邮箱 IMAPS 和正式版读取器，以只读方式选择 INBOX 与可识别的已发件文件夹，通过 PEEK 读取邮件。只读同步不会更新邮箱的已读标记，不启动发件调度或接待，也不调用 SMTP、模型、CRM 或飞书。业务页需指向同一隔离库（`OUTREACH_DB_PATH`）和同一邮箱注册目录（`OUTREACH_DATA_DIR`）。用临时快照同步只影响该快照，访问正式服务的运行环境需要另行部署验证。

## 验证

2026-11-22 的本地快照含 854 段会话。三个账号的增量 IMAP 读取均成功，新增 0 封。按原文和回复头核对后，7 封外部回信都匹配本邮箱的原发件，其中 3 封已有可关联的后续回信，4 封显示待跟进。另有 1 封待核实回执、28 封自动通知和 42 封退信。这 7 封在快照的 CRM 中均无唯一客户匹配，跟进表显示原发件地址。待跟进表示当前缓存中缺少可关联的后续回信，业务员可打开原线程判断是否需要回复。

对独立 SQLite 副本运行 `node scripts/reclassify-mail-cache.mjs --db <副本的绝对路径>` 可预览已有邮件的邮件分类与业务分类变化。加 `--apply` 会在同一事务中更新副本的分类与索引。更新后再预演，变更数应为 0。

`node --test tests/mail-reply-history.test.mjs tests/mailbox-reader.test.mjs tests/mail-conversations.test.mjs tests/positive-reply-reminders.test.mjs` 覆盖真实回复头、无首封历史、跨账号/收件人误关联、内部与机器邮件、分类分页、只读 IMAP、游标重试、并发和积极回复结案。`npm run benchmark:reply-reads` 以 1,203 封含大正文的合成来信测量首页、积极未回复筛选、后续页和工作台待办，输出重复读取耗时、JSON 字节数和 SQLite 查询计划；运行测试不接触真实账号。

读取接口为 `GET /api/v1/outreach/reply-history?mailboxId=all&kind=reply&businessKind=all&handling=all&page=1`。来信类型支持 `reply`、`inquiry`、`notification`、`unverified`、`bounce`、`unsubscribe`、`complaint`、`internal`、`test`、`all`；业务分类支持 `positive`、`refusal`、`referral`、`notification`、`bounce`、`unverified`、`other`、`all`。处理情况支持 `all`、`answered`、`unanswered`。列表返回分类计数和元数据，原文和附件在收件箱详情中查看。
