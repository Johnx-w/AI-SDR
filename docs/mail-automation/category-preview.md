# 客户大类邮件预览

## 需求适用范围与预期

三个现有品牌邮箱 Honey Badger Blinds、Shuangsheng Shutter、Shutter & Blinds Solutions 分别使用自己的身份、签名及获准具体产品。客户经营角色、邮箱和产品分别选择。

分类直接复用 src/data/acquisition.json 的专业供应商、进口商、贸易商、品牌商、工厂、工程承包商、批发商、服务商、经销商、零售商、其他行业；另保留现行官网事实中的 installer（安装服务商）。分类只接受客户自己官网的 customer_type/customer_types 原文证据，兼营角色分别入类，缺证不猜测。“卷帘”是产品，不是通用客户类别。其他行业同样需要真实角色及产品依据。

| 条件                                                                           | 预期结果                                                                                                 |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| 有同源角色、企业身份、联系地址及产品匹配证据；产品已审核生效且获准用于当前邮箱 | 从完整类别中取一个真实客户，生成首封、第 3 天和第 7 天邮件；显示完整主题、正文、签名、样本依据和实际规则 |
| 同一企业有两种角色证据                                                         | 可以从两个类别分别取到，保留各自角色证据                                                                 |
| 客户已固定其他邮箱                                                             | 排除，不能切换品牌身份                                                                                   |
| 无该类别数据、角色来源不属于客户官网、无有效联系依据、产品不适用或未审核       | 明确说明无合格样本及原因；不替换类别或虚构客户                                                           |
| 修改模板、规则、邮箱、类别、产品或步骤                                         | 旧预览失效，重新生成；旧请求不能覆盖新选择                                                               |
| 更换同类样本                                                                   | 在完整类别中从当前编号之后继续，末尾循环；不取前端已加载第一页                                           |
| 预览中邮箱暂停或额度用尽                                                       | 仍可检查内容；不代表可以发送，不修改发送条件                                                             |

首封使用正式 createOutreachGenerator，跟进使用正式 generateFollowUp；第 7 天先生成本次首封、第 3 天上下文。仅预览当前未保存序列的未来效果，不把新草稿说成历史已发邮件。产品与客户证据不足时拒绝。预览不创建计划、发送任务、预留额度或客户状态变化。离线演示使用独立临时库，页面标明“演示样本（非真实客户）”。

## 实际验证范围

基线 0b726ce。修前命令 `node --test --test-name-pattern='真实预览没有合格样本' tests/outreach-service.test.mjs` 失败：Missing expected rejection，证明指定真实范围时仍静默使用虚构卷帘客户；修后同一断言通过。

隔离 SQLite 有 1,215 份档案：前 1,200 份制造商档案含 4 KiB 大字段但产品不匹配；其后有三个邮箱产品对应的制造商、经销商各两个样本，加多角色、跨域角色和缺证对照。预期类别及产品取自独立夹具原始 facts 和邮箱产品配置。测试逐项核对，不将合成数据声称为生产全量验收。

`node --test tests/category-preview.test.mjs` 经正常 API 分发入口核对三邮箱 × 两类别 × 三步骤共 18 次；无数据工程承包商及产品错配均拒绝。检查分类漏项、多角色错归、跨域来源、签名、品牌串用、未替换变量、第 7 天历史及无业务写入。

`node scripts/verify-category-preview.mjs` 从沟通中心 → 跟进序列 → 编辑序列入口完成相同矩阵、更换样本、无数据对照、编辑失效和 390 px 布局。模型 HTTP 层使用替身，正式内容生成与校验逻辑正常运行，未发送 SMTP。首轮浏览器类别选择到样本出现约 18–300 ms；API 首轮约 5–205 ms。计时包含完整类别取样，不包含真实外部模型耗时。后者取决于模型，第 7 天有三次生成。

本机原客户副本两个作用域共 429 份档案，facts 没有角色证据，只登记两邮箱且推品为空；它不是正式三邮箱数据验收来源。已打开的生产页面可读到三个邮箱身份，但本次桌面激活失败、SSH 管理连接不可达，公网未认证接口返回 401，因此不能据本机副本推断生产分类总数或真实模型输出。生产发布及受限验证状态单独报告。

检查命令：`npm run format:check`、`npm test`、`npm run build`。本机完整测试需设置 DOCLING_PYTHON 为已装 Docling 依赖的 Python；默认 python 是 Windows 商店占位程序。CI 已安装依赖，不能为本任务跳过现有素材测试。

## 遗漏复盘（/retro）

依据 Git 中 fe19842、9ee319d 的实现、测试及交付说明，不推测不可见的个人决策。

1. fe19842 将联系人分页明确写进测试预期，预览默认 dealer/workshop 合成企业，仅已有 accepted 首封能作为真实联系人。测试验证了实现的分页，而没有验证业务真正需要的类别取样及三品牌范围。纠正：在现有 npm test 中加入跨 1,200 条不合格数据的类别取样、三邮箱和无数据对照。
2. 9ee319d 的回归只覆盖两家合成卷帘企业的变量重复和问题数量。这个局部修复通过，却没有揭示邮箱缺失、客户角色和产品混在一个选项中的设计错误。纠正：正常页面入口矩阵同时核对样本、品牌、产品、完整邮件及规则。
3. 旧跟进预览使用合成首封和空历史，内容生成看似成功，但没有代表未来实际序列。纠正：相同客户、身份及产品依据逐步生成真实上下文，并断言第 7 天包含前一步。
4. 仓库已有 Windows/Linux CI；遗漏原因不是“没有 CI”，而是验收断言的业务范围错误。将本次稳定复现写入已有套件，比再增加笼统 AGENTS 规则更直接。浏览器检查保留可复跑脚本，明确离线模型与生产证据差别。

本次也暴露环境导航问题：多个旧工作树及缺少 Python 别名容易造成读错基线或误报失败。本次固定 main 基线和独立工作树，使用已有 Docling Python 重跑完整测试；未修改系统别名或业务配置。
