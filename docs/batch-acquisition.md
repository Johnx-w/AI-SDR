# 批量收录

表单默认目标 20 家，允许 1–200 家。只有飞书确认新增的独立企业计数；更新、重复、失败与不符合客群均不占名额。保持既有官网补全、证据校验和产品分析规则，飞书字段不变。

## 调度与上限

本机后台逐家调度 n8n，单任务独占执行。最多研究目标数的三倍企业，最多搜索 `max(20, 3 × 目标)` 次，累计运行不超过 6 小时。达到目标即结束；候选不足或上限触发标为部分完成。停止操作等待当前企业完成，不撤销已入库结果。网站可正常经营但无公开联系方式时，仍按原研究规则处理，不伪造联系方式或强制补齐。

轮换产品与所选市场内的查询，并将已经处理的域名加入搜索排除列表。同一查询只有排除列表变化后才可再次付费执行，避免固定搜索结果页限制大批量数量，也避免反复为完全相同的搜索付费。

n8n 原生产 Webhook 新增 `batch_mode`：`discover` 只发现候选、`research` 只研究指定候选、`status` 查询指定 `operation_id` 的最终结果；省略参数保留原单次行为。每次发现只执行一条范围内查询，避免分组市场展开后超出搜索预算。n8n 当前实例单次上限为 180 秒，批量总任务由本机调度，而不是一次长达数小时的云端执行。

每次写入返回记录 ID 后，通过飞书只读入口再次确认 ID 与域名，再增加新增计数。发生网关超时只查询同一操作，绝不自动重放研究或新增。结果仍不明确则暂停，继续时再次核对。n8n 保存最近 1000 个操作结果，任务队列及完整结果保留在本机 SQLite。

## 接口

- `POST /api/v1/integrations/n8n/jobs`：原业务参数加 `target_count`，必传 `Idempotency-Key`。立即返回 202 和任务快照。
- `GET /api/v1/integrations/n8n/jobs`：最近 100 个任务。
- `GET /api/v1/integrations/n8n/jobs/:id`：进度和企业结果明细，前端每 5 秒查询。
- `POST /api/v1/integrations/n8n/jobs/:id/stop`：停止追加处理。
- `POST /api/v1/integrations/n8n/jobs/:id/resume`：核对当前操作后继续暂停任务；未确认时返回 409，不重复新增。

运行状态为 `running / stopping / paused / completed / partial`。客户端只收到业务进度与结果，不收到认证信息。批量任务活跃或待核对时，旧 `/runs` 入口也禁止并行。

## 持久化与恢复

使用 Node.js 24 的内置 SQLite，正式入口默认 `.data/acquisition.sqlite`，可通过 `BATCH_DB_PATH` 指定路径。数据库及 WAL 不纳入 Git；备份时应停服务或使用 SQLite 一致性备份，不能仅复制运行中的主文件。保留现有 `.env` Webhook 配置即可，不依赖失效的 n8n Public API key。

关闭网页不停止后台；关闭本机服务会中断调度。再次启动后任务暂停，当前未完成企业通过原操作编号核对。若 n8n 自身终止且未生成最终结果，任务会继续保持待确认，需在 n8n 查看该执行，不能把超时直接当成没有写入。

## 验证

`tests/batch-jobs.test.mjs` 验证 1、20、200 家模拟任务、重复跳过、失败补找、停止、预算、幂等和重启恢复。`tests/batch-api.test.mjs` 验证立即接收和接口冲突处理。`scripts/verify-batch-live.mjs` 是会使用真实额度并写入飞书的人工验收脚本，不属于自动测试；运行前须有相应授权。

2026-10-20 已完成真实验收：先运行目标 1 家，飞书从 13 条增至 14 条；再运行目标 5 家，从 14 条增至 19 条。两个任务的新增数量、记录 ID 和官网域名均与飞书读回结果一致；原记录保留。还通过生产 Webhook 读取了已完成操作缓存，确认结果核对入口可用。200 家只做模拟验证。
