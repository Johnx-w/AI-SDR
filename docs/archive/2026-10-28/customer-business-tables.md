## 操作顺序

1. 选择 T2 中已有的企业，新建会话，登记沟通渠道、我方对外账号、客户联系入口及接待归属。
2. 在 T3 登记实际收到或发出的消息、留言或电话纪要，核对时间、收发方、原文和实际结果；勾选实际发生确认。此处没有把草稿发送给客户的操作。
3. 从客户实际来信或确认电话纪要登记 T1 采购需求，选择原文连续摘录，补充产品、规格、数量、负责人和阶段。同一条来信可以登记多项需求。未知字段留空，未匹配到 T5 不阻止登记客户真实需求。
4. 按需要关联 T5 产品资料。待审核、未来生效或已变更版本会明确提示；引用资料不代表已经确认报价或能够满足客户全部规格。
5. 从需求安排 T4 跟进任务，明确人工执行或系统计划、负责人和具体执行时间。本期新建页面默认人工执行，不使用固定的 1/3/5/7 天节奏。
6. 推进前点击任务核验；实际完成后登记执行结果。沟通类任务关联真实已发送消息，内部行动填写明确说明。暂停、恢复、取消及完成均保留执行记录。

## 表格关系

| 业务表              | 实际关联字段                                                         | 主要内容                                                                   |
| ------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| T1 采购需求表       | 客户 → T2；产品资料 → T5；来源沟通 → T3                              | 需求编号、会话、品类、供货方向、规格数量、原文依据、负责人、阶段和资料版本 |
| T3 多渠道沟通记录表 | 客户 → T2；关联需求 → T1                                             | 沟通编号、会话、原文、收发方、渠道、时间、实际结果和外部消息编号           |
| T4 跟进任务表       | 客户 → T2；产品资料 → T5；关联需求 → T1；关联沟通及执行结果沟通 → T3 | 行动、执行方式、时间、负责人、状态、核验提示及实际执行记录                 |

飞书关联使用真实记录 ID，不把公司名称或产品名称当作关系键。会话和客户固定邮箱在后台持久维护，飞书通过会话编号和对外账号查看相应业务内容。T2 客户详情的「沟通与跟进」可以反查需求与任务，T5 产品资料的「关联需求与跟进」可以反查该资料参与的业务。

企业画像的「公开采购需求」继续用于公开来源证据；客户私信形成的实际采购需求保存在 T1，不覆盖该字段或人工开发状态。T2 的 26 列和 T5 的 21 列保持原有结构。

## 状态与执行

- 人工接管暂停对应系统计划，保留人工任务；同一会话下独立需求的接待归属分别核对。
- 客户新回复使旧跟进依据失效，相应任务暂停，处理消息后重新选择依据并明确恢复。
- 明确拒绝联系、硬退信、投诉及已关闭的会话或需求按适用范围处理；企业范围拒绝会影响其他渠道的新沟通任务。
- 产品资料变更、未审核或尚未生效，会在执行前核验时提示。资料版本重新核对不能替代具体商务承诺批准。
- 已经实际发生的消息原文不可改，可补充关联需求及备注。实际发送失败和结果未知独立保留，不计作已成功联系。
- 当前新增功能登记业务和核验任务，不自动发送邮件、WhatsApp、留言或外呼；邮箱连接试点继续遵循其原有授权。新增渠道收发能力及真实自动触达需按现有 ADR-0007 接入。

## 持久化、同步与接口

`CUSTOMER_BUSINESS_DB_PATH` 可指定独立数据库，否则复用获客数据库。记录按客户主表范围隔离，创建使用持久幂等键，编辑使用当前版本，原文与来源关系受到校验。业务记录在网页维护，飞书为协作镜像；直接在飞书新增或改动不会自动导入后台记录图。

业务镜像先核对 T2 与 T5，再创建稳定编号记录，最后写入 T1/T3 的循环关联和 T4 引用。只有完整关联读回一致才报告成功，异常显示待核对，本地记录保留；可手动核对同步而不重复录入。`BUSINESS_MIRROR_JOURNAL_PATH` 可指定异常写入核对日志，默认位于 `.data/`。

- `GET /api/v1/business`：企业、产品及记录图，支持 `customerId`、`productId` 筛选。
- `GET /api/v1/business/schema`：当前业务结构版本与飞书三表配置。
- `POST /api/v1/business/{conversations,messages,demands,tasks}`：新增，要求 `Idempotency-Key`。
- `PUT /api/v1/business/{conversations,messages,demands,tasks}`：修改，要求 `id`、`expectedVersion`；消息仅允许关联与备注修改。
- `POST /api/v1/business/tasks/:id/preflight`：按最新事实核对任务，明确返回 `automaticSend:false`。
- `POST /api/v1/business/tasks/:id/action`：记录完成、暂停、恢复或取消；沟通完成要求实际发送证明。
- `POST /api/v1/business/sync`：重新核对当前记录图的飞书同步。

## 建表与生效

`npm run business:provision` 先保存一致性数据库备份及飞书结构、记录快照，再建立三张表及其单向关联，核对 T2/T5 字段与数据未变。重复执行不会重复建表，未知创建结果先读回核对。备份位于 `.data/backups/t1-t3-t4-20261024/`。

代码完成后，在原服务 PowerShell 窗口按 `Ctrl+C`，再运行 `npm.cmd start`，保持窗口开启。`/api/v1/business/schema` 返回 `schemaVersion: t1-t3-t4-v1` 且飞书配置就绪，表示新版已加载。
